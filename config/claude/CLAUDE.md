# コミュニケーション

## 完了報告

- 「完了」宣言前に user の元指示と逐項目対応表で突合せ、差分を明示。曖昧な完了は差戻しループを招く。

## 曖昧要件の扱い

- 「いい感じに」「適切に」「リッチに」系の指示は、分類カテゴリ / 出力スキーマ / 閾値 を列挙して user に書面合意してから実装に入る。
- 方向性判断 (方式・方向・条件) は 2 案以上の比較表で user 合意後に実装。実装後の方式書換えはコスト最大。

## 仕様文言の解釈

- warn / error / 要件の原文は逐字引用で user 確認。要約した解釈で分岐を増やさない。

# Git / PR 規約（全リポジトリ共通）

- ブランチ名は原則 `topic/<Jira ticket ID>` または `feat/<Jira ticket ID>`。topic=統合ブランチ(スタック開発の基点)、feat=個別実装。
- PR タイトルは `[<Jira ticket ID>]タイトル`（角括弧直後スペースなし）。
- PR 本文は必ずリポジトリの PR テンプレート（`.github/pull_request_template.md` / `.github/PULL_REQUEST_TEMPLATE/`）に準拠。テンプレートを読まずに `gh pr create` しない。
- PR 作成手順の詳細は create-pr Skill に従う。

# モデルオーケストレーション（メインモデルが Fable の場合）

- Fable は設計・思案・レビュー・意思決定に徹する。実装・調査・機械的作業は Agent tool で sonnet / opus 等に委譲する（`model` パラメータを明示指定）。
- 委譲された下位モデルには「自身の手に負えないと判断したら、状況と詰まった点を要約して返す」ことを指示に含める。返ってきたら Fable が直接対処するか、上位モデルで再委譲する。
