# sanitize-artifacts

出典: [kotek-7/dotfiles `dot_agents/skills/sanitize-artifacts`](https://github.com/kotek-7/dotfiles/tree/main/dot_agents/skills/sanitize-artifacts)(2026-08-25 取得・日本語化と K 環境向け節を追加)

セッション中に作った成果物を点検・清書・品質確認するよう求められたときに使う。反復プロンプト・訂正指示・例示・制約提示を重ねて作った成果物ほど効く。

## 目的

成果物が、それ単体で完結した最終成果物として読める状態にする。

成果物に以下の痕跡を不必要に残さない。

- K のプロンプト
- 会話履歴
- 中間推論
- 実装上の制約
- ツール選定の経緯
- 採用しなかった案
- プロンプト運用上の指示
- 制作中に使った足場
- 意図を伝えるためだけに出された例
- 会話中の訂正フィードバック

読者に向けて意図的に設計されたものに見せる。会話から寄せ集めた継ぎ接ぎに見せない。

## 中核原則

会話は **制作コンテキスト** であって、自動的に成果物の内容になるわけではない。

成果物に残す前に、各記述を次の 3 分類のどれかに割り当てる。

1. 読者が本当に必要とする内容
2. 成果物の設計に反映させるが、可視化してはいけない制作ガイダンス
3. 除去すべき会話残滓

直接書いてよいのは 1 のみ。

2 は、構造・トーン・スコープ・前提・既定値・例示・命名・設計判断として **間接的に** 反映する。

3 は削除する。

## 除去・書換の対象

以下を言っている、あるいは含意している箇所を探して、除去または書き換える。

- 「ご指示のとおり」「ご要望に従い」「今回の依頼では」
- 「前回版と異なり」「当初案では〜だったが」「〜から変更した」
- 「〜は使いません」「〜は行いません」「これにより〜を回避します」
- 「〜という制約のため」「本書は〜を前提とする」
- 「この節は〜のため追加した」「要件を満たすため」
- 「会話の中で」「プロンプトでは」「これまでのやり取りで」
- 「Git / Homebrew / CLI は使いません」のような、採用しなかった手段の宣言

機械的に消さない。読者が本当に知る必要がある場合だけ残す。

## 例示は成果物にしない

意図を伝えるために K が出した例は、その成果物自体が必要としない限り、成果物に写し取らない。

会話中の例は通常、最終成果物の内容ではなく診断材料である。例からは次を読み取る。

- 望ましい抽象度
- 読者
- トーン
- どの種類の漏れを避けるべきか
- どういう不自然な言い回しを消すべきか
- どの設計制約が効いているか

例が成果物の主題にすり替わらないようにする。

## 制約は不可視にする

K が出した制約は、通常は成果物の設計に効かせるものであって、断り書きとして表に出すものではない。

悪い例:

> 本ガイドでは Git・Homebrew・追加の CLI ツールは使いません。

良い例:

> プロジェクトフォルダは Google ドライブで共有します。

良い例は、制約を制作上のルールとして露出させずに適用している。

## 点検チェックリスト

1. 会話を見ていない人が読んで自然に読めるか
2. なぜこう書いたのかを説明している文が混ざっていないか
3. ツール・除外・制約・不採用案への不要な言及がないか
4. プロンプト中の例が成果物の一部になっていないか
5. 複数回のフィードバックによる継ぎ接ぎの跡がないか
6. トーン・用語・前提が全体で一貫しているか
7. 見出しや注記が、制作者ではなく読者に向けて書かれているか
8. 制作過程にのみ属するメタコメントが残っていないか
9. 断り書き・注意書きが、読者に本当に必要な場合だけ入っているか
10. 成果物全体が単一の声で書かれているか

## 改稿方針

説明するのではなく書き直す。

会話残滓は、成果物の設計そのものに変換して消す。変換の例:

- 「難しい用語を使わない」→ 平易な語彙にする(「用語は平易にしています」とは書かない)
- 「CLI のブラックボックスを避ける」→ 具体的で追える手順にする
- 「Git ではなく Google ドライブを使う」→ ドライブ前提の手順として書く
- 「初心者向けに」→ 説明の刻み・用語定義・例示に反映する
- 「X に触れない」→ X を書かないこと。「X は扱いません」と書くことではない

成果物の目的・技術的正しさ・読者に必要な要件は保つ。

## 出力ルール

サニタイズを依頼されたら、改稿後の成果物そのものを出力する。

次のような制作過程の前置きを付けない。

- 「メタ指示を削除しました」
- 「プロンプトの漏れを整理しました」
- 「サニタイズ版はこちらです」

短いラベルは、明確化に必要な場合のみ許容する。

成果物と変更サマリの両方を求められた場合は、成果物を先、サマリを後に置く。

## 品質基準

改稿後の成果物は、意図的で・統一されていて・読者にとって自然なものになっていること。

読者が、プロンプトの履歴・内部制約・訂正のやり取りを推測できてはいけない。それらが成果物の内容として本当に必要な場合を除く。

## K 環境での運用

### 主な対象成果物

- Confluence 仕様書(`spec-review` skill で公開する直前)
- PR 本文(`create-pr` skill で本文を組んだ後)
- Jira チケット(`create-tickets` skill)
- Slack 投稿・アナウンス
- `plans/` 配下の申し送り・引継ぎ文書

### AGENT.md §2「逐項目突合せ」との関係

AGENT.md §2 の「完了宣言の前に元指示との逐項目突合せで差分を明示する」は **チャット応答側の義務**。本 skill の「サニタイズ内容を報告しない」は **成果物本体に書かない** という意味であり、突合せ報告はチャットで従来どおり行う。両者は排他ではない。

### トーン設計を壊さない

レビュー前文書の仮置きトーン(「〜が無難そう」)、「合意」ではなく「会話」という語彙、パネル装飾を使わない体裁は、K が意図して選んだ設計(メモリ `feedback_spec_doc_tone`)。サニタイズを口実に断定調へ直したり装飾を足したりしない。

### PR テンプレートの節は対象外

crm-server の PR テンプレート(AI エージェント利用確認 / JIRA / 概要 / 動作確認観点 / コンチプラン)は監査要件であり、読者が必要とする内容(分類 1)。省略・圧縮しない。

### 適用範囲外

- メモリファイル(`~/.claude/projects/*/memory/`)
- オープンループ台帳(`~/.claude/loops.md`)

これらは制作コンテキストを残すことが目的のため、サニタイズしない。
